# NanoServeLab 项目章程

本文件只描述长期稳定的目标、边界和阶段完成标准。当前进度与下一任务统一查看 `docs/project/README.md`。

## 项目定位

NanoServeLab 是一个基于官方 `GeeeekExplorer/nano-vllm` 的轻量级 LLM 推理评测与调度研究项目。项目目标不是重写推理引擎，而是在可理解、可验证的上游实现上建立实验基础，并研究单卡消费级 GPU 上的混合请求调度。

## 研究问题

在单张消费级 GPU 上，面对长短混合的在线 LLM 请求，长度感知、等待时间感知以及 Prefix Cache 感知调度，能否在不显著降低吞吐量的情况下改善 TTFT、TPOT、尾延迟与公平性？

## 上游关系

- 保留官方 LICENSE、源码和 Git 历史。
- `upstream` 只跟踪官方仓库，任何情况下都不得向其推送。
- 不从头重写已经工作的上游组件，也不以 AI 生成替代实现覆盖它们。
- 对 Scheduler、Sequence 或 KV Cache 的研究性修改必须小步进行、配套测试并解释行为变化。
- NanoServeLab 自有研究、实验、结果和项目文档应与上游代码清楚分层。

## 环境分工

- MacBook M4：代码开发、源码阅读、CPU 轻量检查、数据分析和文档。
- Windows WSL2 + RTX 4060：CUDA 推理、完整依赖验证和正式 benchmark。
- macOS 不安装 CUDA-only nano-vLLM 依赖，不在仓库根目录运行 `uv sync`，不为了兼容 Mac 修改上游 `pyproject.toml`。

## 阶段路线与退出标准

### 阶段 0：基础理解与可观测性

- 能解释请求生命周期、Prefill/Decode、Scheduler 队列、KV Block 和 Prefix Cache。
- 用最小 CPU 测试固定关键生命周期行为。
- 建立不改变调度策略的结构化状态观察基础。
- 明确 Mac 与 WSL2 的环境边界以及实验纪律。

### 阶段 1：nano-vLLM Baseline

- 核实 WSL2 GPU、驱动、CUDA 与 Python 环境。
- 固定模型、依赖版本、硬件信息、随机种子和 workload。
- 跑通官方 baseline，重要实验至少重复三次。
- 保存原始结果；只报告实际观察，不推断不存在的性能提升。

### 阶段 2：指标与混合负载

- 定义并验证 TTFT、TPOT、E2E、Throughput 与 Queue Time 的测量边界。
- 构造可复现的长短混合 workload。
- 区分热身、测量和数据汇总阶段，保持单变量实验。

### 阶段 3：调度策略比较

- 建立 FCFS baseline。
- 逐一比较长度优先、Priority 与 Aging；一次只改变一个变量。
- 同时报告吞吐、延迟、尾延迟和公平性，不隐藏负面结果。

### 阶段 4：Prefix Cache 感知扩展

- 在 Prefix Cache 命中行为已验证后，再设计感知调度。
- 分离 Cache 命中收益与调度策略收益。
- 用重复实验验证，不把单次运行当作结论。

### 阶段 5：报告与项目交付

- 整理可复现实验脚本、原始结果、图表和报告。
- 更新用户 README、研究结论和演示材料。
- 清理临时文件、过时文档和未使用的实验分支。

## 实验纪律

- 记录硬件与软件版本。
- 固定随机种子和输入数据。
- 每次实验只改变一个变量。
- 重要 benchmark 至少重复三次。
- 先保存原始结果，再进行汇总和解释。
- 如实报告失败、无提升和退化结果。
- 未经真实重复实验，不声称任何性能提升。

## 教学与开发原则

- 项目所有者必须理解关键调度和实验代码，而不是只获得最终代码。
- 修改 Scheduler 或 KV Cache 前先解释概念、现状和预期不变量。
- 行为变化必须配测试；文档变化不得假装成行为验证。
- 任务保持在当前阶段内，避免同时扩展基础设施、指标与策略。
- 优先选择可独立审阅、可回退的小型纵向切片。
